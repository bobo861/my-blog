### 应用层（1）Web与HTTP

```
应用程序在端系统上以进程的形式呈现
进程利用socket（套接字）发送/接受消息
```

#### 网络程序的期望

* 可靠（有些应用（如语音对话）可以容忍一定数据丢失）
* 高吞吐
* 低时延
* 安全

#### 实际传输层提供的服务

```
tcp
面向连接：传输前建立连接
可靠传输：丢包重传
有序传输
流量控制：防止接收方过载
拥塞控制：防止网络核心过载

无法保证：延迟, 吞吐量, 安全
udp
无连接
不可靠传输：可能丢包，丢包也无法回复

无法保证：可靠性、顺序、流量控制、拥塞控制、延迟、吞吐量、安全

思考：为什么还会有UDP
简单、性能比TCP好、有些应用可以采用
```

> 网络应用层的抽象可以屏蔽底层细节，抽象，安全，简化网络应用开发
>
> 例子
>
> TCP & UDP 
>
> 没有加密功能
>
> 在网络上进行明码传输
>
> SSL + TCP
>
> 提供TCP数据加密
>
> 保证隐私与数据完整
>
> 可以在传输另一端验证
>
> 不再传输明码，而是加密后的数据

#### 应用层的通信实体

* 应用层的实体就是应用程序

* 问题：对于接收到的消息，需要区分是发给哪个应用程序
* **解决方案**：为每个应用以IP地址+端口号命名

#### **应用程序的组织架构**

```
客户/服务器（C/S, Client/Server）方式
含义： 应用APP是一个客户端，服务器和客户端是两个进程
特点： 客户端可以临时接入，ip端口动态，而互相之间不能通信
	  而服务器必须始终在线，ip端口固定，可以与多个实体共同完成任务
分类： 根据是否建立连接：可以是面向连接的（TCP），也可以是无连接的（UDP）
	  根据服务器进程的实现方式：循环（一个一个执行，有阻塞机制）还是并发
e.g. 面向连接（TCP）的并发：
服务器监听一个（熟知, well-known）服务端口，如HTTP的80端口
主服务进程在熟知端口等待客户进程发出的请求，使用的套接字称为服务套接字或者监听套接字
一旦收到客户的请求，就创建一个从属服务进程，并指明从属服务进程使用临时套接字（又称连接套接字）与该客户建立TCP连接
然后主服务进程继续在原来的熟知端口等待向其他客户提供服务
e.g. 为什么无连接的UDP只能采用循环方式，无法采用并发方式
原因：无连接UDP只有一个套接字，无法被多个从属进程同时访问
需要调用额外的操作系统功能，协调多进程访问
```

![C/S架构](/images/computer-network/cs-architecture.png)

```
P2P方式
对等方式是指两个进程在通信时并不区分服务的请求方和服务的提供方
    只要两个主机都运行P2P软件，它们就可以进行平等、对等的通信
    双方都可以下载对方存储在硬盘中的共享文档，如果权限允许的话
音频/视频应用推动了P2P对等通信方式的发展
    音频/视频流量已占主要比例
特点：
    不需要总是在线
    实体可以随时进入退出
    任意两个实体可以直接通信
    易于扩展
```

### HTTP协议

#### 服务

* 在传输层通常使用TCP协议，缺省使用TCP的80端口

* HTTP为无状态协议，服务器端不保留之前请求的状态信息

> 无状态协议：效率低、但简单
>
> 有状态协议：维护状态相对复杂，需要维护历史信息，在客户端或服务器出现故障时，需要保持状态的一致性等

```
HTTP 1.0 执行过程
用户输入URL->浏览器解析->（因为请求结束后马上关闭TCP连接）如果页面包含图像又需要建立完整连接
HTTP 1.1 改为持久连接
HTTP 2   请求/响应允许交错，可以自定义优先级
		 服务器可以主动推送消息
		 允许应用层进行流量控制
HTTP 3   传输层的变化 TCP-> UDP+QUIC
```

> 三次握手连接建立
>
> Request （Get /index.html）
>
> Respone
>
> 关闭连接

#### HTTP缓存

* 浏览器保存主机中的web页副本

* 代理服务器

  ISP安装Web代理缓存服务器，保存ISP客户访问过的服务器Web页副本

  副本可以供ISP的所有客户访问，提高访问服务器的Web页效率

```
与浏览器缓存同样的一致性问题：Web缓存与原始服务器Web对象一致性问题
* 启发式缓存更新策略（原始服务器发起）：服务器响应包含Last-Modified字段和Expires字段
    少用，原因：服务器很难确定expires字段该设置什么值
* 询问式缓存更新策略（代理服务器/客户端发起）：通过特殊的关键字头If-modified-since询问原始服务器，Web副本是否已更新 
    询问式策略：通过特殊的关键字头询问原始服务器，Web副本对应的原始Web页是否已更新 
    客户端：在发送的HTTP请求中指定缓存的时间，请求头包含If-modified-since: <date>
```

* 特殊场景：服务器禁止缓存

  服务器返回web页时，带一个no-cache禁止缓存

  需要授权登录

#### cookie

```
HTTP无状态协议，服务器用cookies保持用户状态
服务器在HTTP响应的首部行里使用一个关键字头set-cookie，服务器分配的cookie内容具有唯一性
后继的HTTP请求中使用服务器响应分配的cookie，表明这个请求是之前请求的后续
Cookie保存在用户的主机中，由浏览器管理
Web服务器建立后端数据库，以cookie作为关键字，记录相关信息
```

![Cookie流程](/images/computer-network/cookie-flow.png)

> cookie 字段
>
> 域 + 路径 + 内容 + 过期 + 安全
>
> •域指明Cookie来自何方，每个域为每个客户分配Cookie有数量限制
>
> •路径标明服务器的文件树中哪些部分可以使用该Cookie
>
> •内容采用“名字=值”的形式，是Cookie存放内容的地方，可以达到4K容量，内容只是字符串，不是可执行程序
>
> •安全指示浏览器只向使用安全传输连接的服务器返回Cookie
